# Judge ledger bootstrap — local candidate

This image initializes the **real judge service's** ledger and private receipt directory on a new InstaCloud volume. It has not been deployed. A separately approved operator must select the exact project, service, region, volume and HTTPS exposure before any platform action. This is distinct from the synthetic `incidentcourt-fixture` bootstrap and does not itself prepare a working judge service.

Build a minimal context containing `incidentcourt/__init__.py`, `incidentcourt/quota.py`, and `deploy/instacloud/bootstrap_guard.py`, `bootstrap.py`, and `bootstrap_health.py`, with `deploy/instacloud/Dockerfile.bootstrap` as its root `Dockerfile`. This context it contains no Nebius client, telemetry, judge app, credentials or `.env` file. The source Dockerfile uses the locally inspected base digest `python:3.12-slim-bookworm@sha256:6a0e06f5ba0b373d051aabd3fffb9b873f27f9a2a3a14bcbe37dee6f0e3bbc70`. Verify the exact context contents and intended architecture/digest before using a remote builder. The local ARM64 image is `incidentcourt-judge-bootstrap-qa:pinned-20261029`, local image ID `sha256:5ffc89a4cecec04b10f60b4b4886ace7c19fcc7465a5b3cfc2175ca7efd88823`; a remote amd64 build will have a different image ID and is not verified by this test.

The image's normal process exposes only `GET /health` on port 8080. Its response identifies `judge-ledger-bootstrap-only`, reports whether `/data` is a mountpoint, and reports zero provider calls. It does not read or initialize the ledger over HTTP or at process startup; other paths fail and POST is unsupported. It rejects any `NEBIUS_*` or `JUDGE_ACCESS_CODE` environment variable, even an empty one. The bootstrap and health processes block Python outbound socket connections; the image contains no provider client. These are application-level safeguards, not a host firewall against arbitrary code executed through an authorized console. The `/health` endpoint is unauthenticated and may be publicly reachable; it contains no private data, but traffic can consume hosting credit. Keep exposure brief and restrict ingress if supported.

## One-time operator workflow after separate approval

1. Deploy this reviewed **health-only** image to a new dedicated service with a new 1 GiB volume attached at `/data`, port 8080, and no provider or judge credential variables. The Free plan's shared credits can be consumed; confirm actual plan, usage and terms at action time. Obtain separate approval for resource creation and deployment. A default image may start when the service is created, so inspect the platform's exact creation behavior before acting.
2. Request `/health` over the actual HTTPS URL and confirm `volume_mounted: true`. This confirms only mountpoint detection, not that it is the intended persistent volume. Independently inspect the volume identity, `/data` ownership and write access for UID 10001. On the earlier **fixture** service, cloud exec defaulted to UID 0 and `runuser -u investigator` could write its new volume; that does not prove this service will behave identically. Stop if the volume is not the intended new volume or UID 10001 cannot safely write it. Do not modify ownership or run as root without a separately reviewed/approved fix.
3. Explicitly invoke the initializer once inside the running health-only image. The verified local image includes `/usr/sbin/runuser` and an `investigator` user with UID 10001. If the platform's console exec runs as root, the proposed command is:

   ```text
   insta compute exec <approved-judge-service> -- runuser -u investigator -- python -m deploy.instacloud.bootstrap --initialize-new-volume
   ```

   If exec already runs as UID 10001, omit `runuser -u investigator --`. `insta compute exec` may wake a stopped machine and consume platform credits. Confirm actual exec UID and command availability on this service before execution. The initializer rejects missing/non-mounted `/data`, any UID other than 10001, credentials, and any existing `/data/incidentcourt` directory. On the first successful run it creates `/data/incidentcourt` and `provider-receipts` as 0700 and `quota.sqlite3` as 0600, then syncs directory entries. If the command fails after making any files, inspect the exact partial state and seek an approved recovery; do not delete it, rerun with auto-reset, or create a replacement ledger to mask prior usage.
4. Verify ownership, permissions, the empty ledger and receipt directory without disclosing their private contents. Retire this health-only image and deploy the **separately reviewed** judge image to the same service and same volume only after the appropriate approvals. Recheck volume identity and ledger persistence across redeployment and a real idle stop/wake. Do not transfer the Nebius key or create a judge credential until separately approved. The judge gateway must fail closed on missing or replaced ledger/receipt storage and must never auto-initialize on restart.

## Local evidence and limits

The provider-free bootstrap image was built with build networking disabled from the cached pinned base. In a network-disabled Docker container with a newly created disposable volume, health returned the expected result, POST was rejected, no ledger appeared automatically, and a root console used `runuser -u investigator` to initialize the private files as UID 10001. A second initialization failed without changing the ledger, and a container restart preserved its bytes. A synthetic `NEBIUS_API_KEY` caused startup rejection, and the image had no importable `incidentcourt.nebius` module. The disposable container and volume were removed. Local unit tests also exercise rejection of root/wrong UID, credential variables and missing mounts.

These checks do **not** prove remote image build, platform exec identity, the intended volume's ownership or integrity, automatic idle-stop/wake, public HTTPS behavior, actual Nebius inference, no billed charges, or readiness for judges. Consult [judge gateway preparation](../../docs/JUDGE_HOSTING_PREPARATION.md) for the remaining access, billing, and verification gates.
